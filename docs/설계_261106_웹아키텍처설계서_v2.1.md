## 1. 전체 구조

```
브라우저 (Jinja2 HTML + CSS + Vanilla JS + Chart.js)
   │  HTTP (페이지는 HTML, 데이터는 /api/* JSON, 상태 변경은 CSRF 토큰 필수)
   ▼
Flask 앱 (app.py: create_app 팩토리)
   ├─ 웹 계층   src/web/        auth_routes · user_routes · admin_routes · security
   ├─ 업무 계층 src/business/   AuthManager · WordManager · StudyManager · TestEngine
   │                            ReportGenerator · GamificationManager  (+ src/utils/config.py SettingsManager)
   └─ 데이터 계층 src/data/database.py  Database (sqlite3 헬퍼)
   ▼
data/smart_voca.db (SQLite, WAL)  /  data/secret_key.txt   ← 둘 다 gitignore
```

설계 원칙
- 라우트는 입력 검증과 응답 변환만 하고, 규칙은 업무 계층에 둔다. (예: `user_routes.api_record_study` → `StudyManager.record_study`)
- 서비스 객체는 `create_app` 에서 한 번 만들어 `app.db`, `app.auth`, `app.words`, `app.game`, `app.study`, `app.tests`, `app.reports`, `app.settings` 로 붙이고, 라우트는 `current_app.*` 로 쓴다. 객체는 요청 간 공유되지만 사용자별 상태는 전부 DB 에 있다.
- 업무 계층의 오류는 `AuthError`, `WordError`, `TestError`, `SettingsError` 로 던지고, 라우트가 `json_error()` 로 400 응답으로 바꾼다. 이 예외의 메시지는 사용자에게 그대로 보여도 되는 문장으로 쓴다.

### 3.4 공통 처리 (`app.py`)

- `before_request.load_user`: 세션의 `user_id` 로 사용자를 읽어 `g.user` 에 둔다. 비활성·삭제 계정이면 세션을 지우고 `g.kicked=True`. 이어서 `check_csrf()`.
- `context_processor`: 템플릿에 `current_user`, `csrf_token` 주입.
- `after_request`: 보안 헤더 3종과 `.js`/`.css` Content-Type.
- 오류 핸들러 400/403/404/413/500: `/api/*` 또는 JSON 요청이면 `{"error": 메시지}`, 아니면 `error.html`.
- 정적 파일 라우트 3개(`serve_js`, `serve_css`, `serve_static`)는 Flask 기본 static 과 중복이라 제거했다(`5b29d2c`). MIME 은 `mimetypes.add_type` 으로 처리하고, `after_request` 의 `.js`/`.css` Content-Type 덮어쓰기는 유지 중이다 (§8 #1 참고).

## 4. 데이터 설계

### 4.1 테이블 (`src/data/database.py: SCHEMA`)

| 테이블 | 키 | 주요 컬럼 | 비고 |
|---|---|---|---|
| `users` | PK id | username(UNIQUE), display_name, password_hash, role('user'/'admin' CHECK), active, daily_target(기본 10), theme(기본 'system'), created_at | |
| `words` | PK id | english(UNIQUE, NOCASE), korean, part_of_speech, example, created_at | 전 사용자 공유 |
| `user_word_stats` | PK (user_id, word_id) | weight, success_count, fail_count, last_studied | 사용자·단어 삭제 시 CASCADE |
| `study_logs` | PK id | user_id, date, words_count, correct_count, success_rate, duration | 인덱스 (user_id, date). `duration` 은 현재 코드에서 쓰지 않는다 (기본 0) |
| `test_logs` | PK id | user_id, date, mode, format, total_problems, correct_answers, score | 인덱스 (user_id, date) |
| `test_sessions` | PK user_id | state_json, updated_at | 사용자당 진행 중 시험 1개 |
| `app_settings` | PK key | value | 전역 설정 `total_days`, `max_test_problems`, `max_daily_target` |

관계: `users 1—N user_word_stats / study_logs / test_logs`, `users 1—1 test_sessions`, `words 1—N user_word_stats`. 외래키는 `PRAGMA foreign_keys = ON` 을 연결마다 켠다.

### 4.2 접근 방식

- `Database.session()` 컨텍스트: 정상 종료 시 commit, 예외 시 rollback. 요청마다 짧게 연결을 열고 닫는다 (스레드 문제 회피).
- `query / query_one / scalar / execute / execute_rowcount` 헬퍼와 `get_setting / set_setting`(UPSERT).
- 여러 테이블을 바꾸는 작업은 한 `session()` 에서 처리한다: `record_study`(통계+로그), `finish_test`(로그+통계+세션 삭제), `reset_user_progress`.
- 모든 SQL 은 `?` 바인딩을 쓴다. 예외로 `reset_user_progress` 의 테이블명은 코드 안의 고정 튜플에서만 가져온다.
- XP 는 컬럼에 저장하지 않고 `study_logs`/`test_logs` 에서 매번 계산한다. 레벨·리그가 로그와 항상 일치하는 대신 조회 비용이 로그 수에 비례한다.

### 4.3 ADR-001: 데이터 저장소를 CSV/JSON 에서 SQLite 로 변경

- **배경**: v1.0 은 `words.csv`, `progress.json`, `study_log.csv`, `test_log.csv` 를 파일 I/O 로 다뤘다. 다중 사용자(로그인), 사용자별 학습 상태, 동시 접속, 관리자 통계 집계가 요구사항이 되면서 파일 방식으로는 기록이 섞이고 동시 쓰기가 위험해졌다.
- **대안**: (1) 사용자별 CSV 파일 분리 — 집계 쿼리와 트랜잭션이 없다. (2) PostgreSQL/MySQL — 별도 서버 설치가 필요해 로컬 시연·과제 환경에 과하다. (3) SQLite — 설치 불필요, 표준 라이브러리 `sqlite3`, SQL 집계·트랜잭션·외래키 지원.
- **결정**: SQLite(`data/smart_voca.db`) + 표준 `sqlite3`. ORM 은 쓰지 않는다 (규모 대비 의존성 절감, SQL 을 직접 학습).
- **결과**: 장점은 트랜잭션, 사용자 격리 쿼리, 관리자 집계, 서버 재시작 후에도 시험 이어하기. 단점은 스키마 변경 시 마이그레이션 수단이 없고(`CREATE TABLE IF NOT EXISTS` 는 기존 컬럼을 바꾸지 않음), 단일 파일이라 다중 서버 확장에 한계가 있다.

## 5. 핵심 흐름

### 5.1 학습 (FR-301~305)

```
GET /study → study.html 렌더
JS: GET /api/study/daily-words → 단어 N개 (오답 가중치 → 미학습 → 오래된 순)
사용자가 단어마다 O/X 선택
JS: POST /api/study/record {results} (X-CSRF-Token 헤더)
 서버: 유효 word_id 필터 → [트랜잭션] update_user_stat × N + study_logs INSERT
 서버 → {xp_gained, level_up, ...}
```

### 5.2 시험 (FR-401~407)

```
POST /api/test/start → 문제 N개를 미리 만들어 test_sessions.state_json 에 저장 (정답 포함, 서버에만)
반복: GET /api/test/current (정답 제외) → POST /api/test/answer → 정오답 즉시 응답, state.index 증가
POST /api/test/finish → [트랜잭션] test_logs INSERT + 단어 통계 반영 + test_sessions DELETE → 결과·XP
```

정답을 클라이언트에 보내지 않는 것이 핵심 설계다 (개발자 도구로 정답을 볼 수 없다).

### 5.3 로그인·세션 (FR-102, FR-104, FR-106)

```
POST /login → login_blocked? → authenticate → session.clear() → session['user_id'] 저장 (7일)
이후 모든 요청: load_user → 사용자 조회 → 비활성이면 세션 삭제 + flash
```

## 6. 보안 설계 (NFR-001~007)

| 항목 | 방식 | 위치 |
|---|---|---|
| 비밀번호 | Werkzeug `generate_password_hash`/`check_password_hash` | `AuthManager` |
| 세션 | 서명 쿠키(HttpOnly, SameSite=Lax, 옵션 Secure), 로그인 시 `session.clear()` | `app.create_app`, `auth_routes.login` |
| CSRF | 세션에 `_csrf` 토큰 생성, POST/PUT/DELETE 는 헤더 `X-CSRF-Token` 또는 폼 `csrf_token` 일치 필수 (`secrets.compare_digest`) | `security.check_csrf` |
| 권한 | 데코레이터 `login_required`, `admin_required`. 관리자 API 는 서버에서 검사 | `security.py` |
| 로그인 제한 | (IP, 아이디) 키로 5회 실패 시 300초 잠금. 프로세스 메모리 딕셔너리 | `security.py` |
| 오픈 리다이렉트 | `safe_next_url` 이 `/` 로 시작하고 `//`·역슬래시 없는 경로만 허용 | `security.py` |
| 데이터 격리 | 사용자 쿼리는 항상 `g.user['id']` 로 조회 (요청 본문의 user_id 를 쓰지 않는다) | `user_routes.py` |
| XSS | Jinja2 자동 이스케이프 + JS `esc()` | 템플릿, `main.js` |
| 업로드 | 요청 3MB 상한, CSV 는 2MB·확장자 검사 | `app.py`, `admin_routes.words_import` |
| 시크릿 | `SECRET_KEY` 환경변수 우선, 없으면 `data/secret_key.txt` 자동 생성 | `app._load_secret_key` |
