## ADR-001: SQLite 데이터베이스 선택

- **상태**: 승인 (2026-11-02)
- **일자**: 2026-10-28
- **요구사항**: FR-101 ~ FR-702 (다중 사용자 데이터 격리)

### 배경 (Context)
- v1.0: CSV 파일로 단어·학습 기록 저장 → 문제: 다중 사용자 동시 접속 시 데이터 섞임, 트랜잭션 불가
- v2.0: 다중 사용자 지원 필요 (5명 이상)
- 로컬 학습용 프로젝트 (프로덕션 배포 없음)

### 대안 (Options)

| 대안 | 장점 | 단점 | 비용 |
|------|------|------|------|
| **SQLite** | 파일 기반, 설정 최소, Python 표준 라이브러리 | 동시 쓰기 제한, 확장성 낮음 | 0 |
| PostgreSQL | 동시성 강함, 확장성 높음 | 서버 설치·관리 필요, 복잡 | 높음 |
| MySQL | 널리 사용됨, 성능 좋음 | 서버 설치·관리 필요 | 중간 |
| 메모리 DB (Redis) | 빠름 | 지속성 없음, 재시작 시 손실 | 중간 |

### 결정 (Decision)
**SQLite 선택** ← 로컬 개발·학습 프로젝트이고, 동시 사용자 5명 정도이므로 SQLite로 충분

### 결과 (Consequences)

**이점**:
- ✅ 설치 간편 (Python 표준 라이브러리)
- ✅ 파일 기반이라 git, USB로 쉽게 이동 가능
- ✅ 트랜잭션 지원 (학습 기록 + XP 동시 저장)
- ✅ 학생 프로젝트에 적합한 복잡도

**제약**:
- ❌ 동시 쓰기 시 LOCKED 에러 가능성 (로컬용이라 수용)
- ❌ 프로덕션 배포 시 PostgreSQL로 마이그레이션 필요

**후속 작업**:
- 배포 시 PostgreSQL로 변경
- 현재: WAL(Write-Ahead Logging) 활성화로 동시성 개선

## ADR-002: Flask Blueprint 3계층 구조

- **상태**: 검토 (2026-11-11)
- **일자**: 2026-10-28
- **요구사항**: 모든 기능 (코드 유지보수성)

### 배경 (Context)
- 라우트 100+ 개 필요 (인증, 학습, 시험, 통계, 관리자 등)
- 한 파일에 다 쓰면 관리 불가능
- 코드 재사용성·테스트 용이성 필요

### 대안 (Options)

| 대안 | 구조 | 장점 | 단점 |
|------|------|------|------|
| **Blueprint 3계층** | web(라우트) → business(로직) → data(DB) | 계층 명확, 테스트 쉬움, 재사용성 높음 | 초기 설정 복잡 |
| 단일 app.py | 모든 라우트·로직을 app.py에 | 빨리 만들 수 있음 | 500+줄 파일, 관리 어려움 |
| MVC (Model-View-Controller) | 기존 Django 방식 | 널리 알려짐 | Flask에는 과함 |

### 결정 (Decision)
**Flask Blueprint 3계층** 구조 채택

```
web 계층 (src/web/):
  ├─ auth_routes.py      (로그인·회원가입)
  ├─ user_routes.py      (학습·시험·통계)
  └─ admin_routes.py     (관리자 기능)
  
business 계층 (src/business/):
  ├─ auth_manager.py     (사용자 인증)
  ├─ study_manager.py    (학습 로직)
  ├─ test_engine.py      (시험 출제·채점)
  ├─ report_generator.py (통계)
  └─ gamification.py     (XP·레벨)
  
data 계층 (src/data/):
  └─ database.py         (SQLite 헬퍼)
```

### 결과 (Consequences)

**이점**:
- ✅ 각 계층의 책임이 명확
- ✅ 라우트는 입력 검증과 응답만 처리 (로직 아님)
- ✅ pytest로 각 계층 독립 테스트 가능 (현재 27개)
- ✅ 새 기능 추가 시 어디 수정할지 명확

**제약**:
- ❌ 초기 설정이 복잡함
- ❌ 파일 5개+ 필요 (단순 기능도)

**후속 작업**:
- 각 모듈별 README 작성 (완료)
- pytest 26개 → 27개 (완료)

## ADR-003: 세션 기반 인증 (JWT 아님)

- **상태**: 검토 (2026-11-11)
- **일자**: 2026-10-28
- **요구사항**: FR-101, FR-103 (인증·로그아웃)

### 배경 (Context)
- 사용자 5명, 로컬 학습용
- 모바일 앱 없음 (웹 브라우저만)
- 로그아웃 기능 필요 (서버가 세션 즉시 무효화)

### 대안 (Options)

| 대안 | 방식 | 장점 | 단점 |
|------|------|------|------|
| **세션** (Flask-Session) | 서버가 session store 관리 | 로그아웃 즉시 반영, 간단, 토큰 갱신 불필요 | 서버 메모리 사용 |
| JWT (JSON Web Token) | 클라이언트가 토큰 보유 | 서버리스, 확장성 높음, 모바일 앱 지원 | 로그아웃 처리 복잡 (블랙리스트 필요) |
| OAuth2 | 제3자 인증 | 보안 높음 | 구현 복잡, 외부 의존 |

### 결정 (Decision)
**세션 기반 인증** 선택 ← 로컬 프로젝트, 로그아웃 즉시성 필요, 모바일 미지원

### 구현 방식
```python
# app.py에서
app.config['SESSION_TYPE'] = 'filesystem'
app.config['PERMANENT_SESSION_LIFETIME'] = timedelta(days=7)

# 로그인 시
session['user_id'] = user.id
session['role'] = user.role

# 로그아웃 시
session.clear()  # 즉시 무효화
```

### 결과 (Consequences)

**이점**:
- ✅ 로그아웃 시 즉시 세션 무효화
- ✅ 토큰 갱신 로직 불필요
- ✅ CSRF 공격 방어 쉬움 (Flask 기본 제공)
- ✅ 구현 간단

**제약**:
- ❌ 모바일 앱 지원 불가 (JWT 필요)
- ❌ 마이크로서비스 아키텍처 미지원
- ❌ 서버가 메모리에 세션 저장 (재시작 시 로그아웃됨)

**보안**:
- ✅ CSRF 토큰 필수 (모든 POST/PUT/DELETE)
- ✅ 로그인 시도 5회 이상 시 5분 잠금 (FR-104)
- ✅ 비활성 계정 세션 자동 무효화 (FR-106)

**후속 작업**:
- 배포 시 Redis/Memcached로 세션 마이그레이션 권고

## ADR-004: 사용자별 데이터 격리 (테이블 설계)

- **상태**: 검토 (2026-11-11)
- **일자**: 2026-11-02
- **요구사항**: FR-202, FR-301, FR-501 (사용자별 진도·단어)

### 배경 (Context)
- 다중 사용자 환경에서 학생 A의 학습 기록이 학생 B에게 보여지면 안 됨 (FR-1-017: 데이터 격리)
- v1.0 CSV: 모든 사용자가 같은 파일 → 기록 섞임
- 동시성, 조회 성능도 고려

### 설계 (Design Decision)

**핵심**: `user_id` 외래키로 사용자 레코드 소유 명시

```sql
-- 사용자별 단어 진도
CREATE TABLE user_word_stats (
    user_id       INTEGER NOT NULL,
    word_id       INTEGER NOT NULL,
    weight        INTEGER,          -- 오답 우선순위
    success_count INTEGER,
    fail_count    INTEGER,
    last_studied  TEXT,
    PRIMARY KEY (user_id, word_id)
);

-- 사용자별 학습 기록 (매일)
CREATE TABLE study_logs (
    id            INTEGER PRIMARY KEY,
    user_id       INTEGER NOT NULL,  -- 소유자
    date          TEXT,
    words_count   INTEGER,
    correct_count INTEGER,
    ...
);

-- 사용자별 시험 진행 상태
CREATE TABLE test_sessions (
    id       INTEGER PRIMARY KEY,
    user_id  INTEGER NOT NULL,  -- 소유자
    ...
);
```

### 쿼리 원칙
모든 쿼리에 `WHERE user_id = ?` 필수 (다른 사용자 레코드 절대 조회 금지)

```python
# StudyManager.get_daily_words(user_id)
def get_daily_words(self, user_id: int):
    sql = """
    SELECT w.id, w.english, w.korean, u.weight
    FROM words w
    LEFT JOIN user_word_stats u ON u.word_id = w.id 
                                  AND u.user_id = ?
    ORDER BY COALESCE(u.weight, 0) DESC
    LIMIT ?
    """
    # 절대로 user_id 빼고 쿼리하지 않음!
```

### 결과 (Consequences)

**이점**:
- ✅ 완벽한 데이터 격리 (다른 사용자 데이터 접근 불가)
- ✅ DB 레벨에서 소유권 명시 (코드 실수 예방)
- ✅ 성능 (인덱스: PRIMARY KEY (user_id, word_id))
- ✅ 동시성 안전 (각 사용자가 다른 레코드 수정)

**테스트**:
- ✅ test_users_data_is_isolated (pytest, 통과)

**후속 작업**:
- 모든 쿼리에서 user_id 검증 계속 (보안 체크리스트)

## ADR-005: 게임화 시스템 (XP·레벨·주간 리그)

- **상태**: 검토 (2026-11-11)
- **일자**: 2026-11-04
- **요구사항**: FR-601, FR-602, FR-603 (게임화)

### 배경 (Context)
- 영어 학습은 반복 학습이 지루함
- 동기 부여 필요 (점수, 등급, 경쟁)
- 일회성이 아닌 지속 가능한 설계

### 대안 (Options)

| 대안 | 방식 | 장점 | 단점 |
|------|------|------|------|
| **XP+레벨+리그** | 행동점(XP) → 누적 레벨, 주간 순위 | 동기 부여 높음, 목표 명확, 사회성 | 구현 복잡 |
| 배지·뱃지만 | 목표 달성 시 배지 | 간단, 개인화 | 동기 부여 약함 |
| 실제 화폐 리워드 | 랭킹 따라 코인 지급 | 극강 동기 | 비용, 부정행위 위험 |

### 결정 (Decision)
**XP + 레벨 + 주간 리그** 선택 ← 학생용이므로 무료이면서도 충분한 동기 부여

### 설계 (Design)

**XP 규칙** (FR-601)
```python
STUDY_CORRECT   = 10  # 학습에서 맞춤
STUDY_WRONG     = 2   # 학습에서 틀림 (0 아님 - 참여 보상)
TEST_CORRECT    = 15  # 시험에서 맞춤
TEST_WRONG      = 3   # 시험에서 틀림
```

**레벨 공식** (FR-602)
```
레벨 n에 도달하는 누적 XP = 50 × (n-1) × n

L1 → L2: 50 × 0 × 1 = 0 (시작)
L2 → L3: 50 × 1 × 2 = 100
L3 → L4: 50 × 2 × 3 = 300
...
```
→ 초반은 빨리, 후반은 느려지는 곡선 (포기 방지)

**주간 리그** (FR-603)
```python
# 최근 7일 동안의 누적 XP로 순위 계산
# 상위 20명 + 본인 표시
# 관리자, 비활성 계정 제외
```

### 결과 (Consequences)

**이점**:
- ✅ 일회성이 아닌 지속 가능한 동기 부여
- ✅ 개인 목표(레벨 달성)와 사회적 동기(리그 순위) 병행
- ✅ 학습 방식별로 다른 XP (시험이 더 많음 = 도전 권장)
- ✅ 정기적으로 리셋되는 리그 (매주 시작 → 매번 기회)

**설계 고려**:
- ✅ 0점 참여 보상 (틀려도 2XP = 포기 방지)
- ❌ 화폐 가치 없음 (순수 동기 부여만)
- ✅ 속임 방지 (일회성 높은 점수 후 쉬기 불가, 일일 학습 장려)

**테스트**:
- ✅ test_xp_level_and_levelup (pytest, 통과)
- ✅ test_weekly_league_ranking_and_exclusions (pytest, 통과)

**후속 작업**:
- 11/16 배포 후 사용자 5명에게 공유해 받은 피드백(이슈 #4 에 정리)으로 XP 값 조정

## 정리: 5가지 핵심 결정

| ADR | 결정 | 이유 |
|-----|------|------|
| **001** | SQLite | 로컬 학습 프로젝트, 다중 사용자 5명 |
| **002** | Flask Blueprint 3계층 | 코드 유지보수성, 테스트 가능성 |
| **003** | 세션 인증 | 로그아웃 즉시성, 간단한 구현 |
| **004** | user_id 외래키 격리 | 완벽한 다중 사용자 데이터 격리 |
| **005** | XP+레벨+리그 게임화 | 지속 가능한 동기 부여 |

각 결정은 **"로컬 학습 프로젝트"** 라는 제약 속에서 **"포트폴리오 완성도"** 를 높이는 방향으로 이루어졌다.
